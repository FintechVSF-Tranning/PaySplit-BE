# Review, lampt/auth-account-v2, 2026-09-10

**Reviewed by**: Claude Sonnet 5 (author on Claude Opus 5)
**Scope**: 17 files, custom feature scope ("Session revocation hardening", scope.md item 11) vs merge-base `1d3171e9f17d17f8fb7c5a8bbe117fcfd331b5d9` + uncommitted work
**Verdict**: Changes requested

## Summary
This slice closes four gaps left in the Redis session backstop: unconditional revocation on repeated account locks, a 401/503 split in the auth middleware so Redis outages don't mass-logout users, a Prometheus alert on purge-job exhaustion, and enforcement of a Redis password plus `noeviction` outside development (with a fail-closed fix for an unset `APP_ENV`). Three of the four follow-ups are solid, well-reasoned, and well-tested. The fourth (unconditional revocation, follow-up 1) has a real gap: the durable `session_redis_purge` backstop job is silently *not* enqueued on a repeat lock of an already-revoked account, so the only enforcement in that path is the synchronous `RevokeUser` call with no async retry behind it if that call itself fails. Test quality across the diff is unusually good — tests assert observable behavior (context values, HTTP status/body, counter deltas, real Lua-script semantics against miniredis) rather than re-describing the implementation.

## Major
### 🟠 Repeat-lock leaves the durable purge-job backstop unenqueued, `internal/modules/admin/repository/postgres/repository.go:250` and `internal/modules/admin/usecase/service.go:191`
**Problem**: `UpdateAccountStatusWithRevocation` only enqueues the `session_redis_purge` River job when the `UPDATE sessions ... RETURNING id` query matches at least one row (it builds `revokedSIDs` from those rows and calls `r.sessionPurge.EnqueueTx(ctx, tx, targetUID.String(), revokedSIDs)`). `SessionPurgeEnqueuer.EnqueueTx` (`internal/modules/auth/jobs/session_purge.go:91`) itself no-ops when `len(sids) == 0`. So on a second lock of an already-locked/suspended account — precisely the scenario follow-up 1 was written to fix — the Postgres `UPDATE` matches zero rows, `revokedSIDs` is empty, and **no purge job is queued at all**. The usecase's synchronous `s.sessions.RevokeUser(ctx, input.TargetUserID)` call (service.go:202) is the *only* enforcement left for that event. If that one synchronous Redis call itself fails transiently (the exact class of failure follow-up 3's alert exists to catch), there is nothing durable behind it to retry — the error is surfaced to the admin caller, but nothing re-attempts the revocation automatically, and no `session_purge_exhausted` metric ever fires because no job was ever inserted.
**Why it matters**: AGENTS.md states the invariant plainly: "Every admin revocation also enqueues a `session_redis_purge` River job inside the same transaction so a dropped Redis write converges." This diff breaks that invariant precisely for repeat locks — the one case follow-up 1 was scoped to fix. A transient Redis blip during a second lock attempt (e.g., an admin re-locking an account because the first attempt looked like it failed) can leave a "locked" account with a live session and zero automated convergence, silently, until someone repeats the admin action again.
**Suggested fix**: Either (a) always enqueue the purge job on a lock/suspend transition regardless of how many Postgres rows were revoked — pass the *current* live SID(s) from Redis (or just re-run `RevokeUser` as the job body, matching the same unconditional semantics used synchronously) rather than gating enqueue on Postgres row count, or (b) have the usecase itself enqueue a fallback purge job when `RevokeUser` succeeds/fails, so the async backstop always exists for a lock/suspend action, not just the first one.

## Minor
### 🟡 Interface doc comment no longer matches what the usecase does, `internal/modules/admin/repository/repository.go:32`
**Problem**: The comment on `UpdateAccountStatusWithRevocation` still says the returned `[]string` of revoked SIDs is "để usecase xoá chúng khỏi Redis sau khi transaction commit" (for the usecase to delete them from Redis after commit). That's no longer true: `service.go:182` discards this slice (`_`) entirely and calls the unconditional `RevokeUser(ctx, userID)` instead, precisely because relying on that SID list was the bug follow-up 1 fixes.
**Why it matters**: A reader trying to understand why the SID list still flows through this interface (only for `NotifySessionEnded`'s pg_notify use, not for revocation) will be misled by a comment describing removed behavior — this is exactly the kind of comment drift that caused the original bug (a gate that quietly stopped doing what its documentation claimed).
**Suggested fix**: Update the comment to say the returned SIDs are used only for the `session.ended` pg_notify signal, and that revocation itself is unconditional in the usecase.

### 🟡 Eviction-policy "unverified" fallback has no metric, only a log line, `internal/platform/redis/client.go:557`
**Problem**: When `CONFIG GET maxmemory-policy` fails or omits the key (managed Redis blocking `CONFIG GET`), `verifyEvictionPolicy` logs `event=redis_eviction_policy_unverified` and returns `nil`, allowing startup to proceed. This is a reasonable trade-off (refusing to boot against every managed Redis would be worse), but this same feature's philosophy — established by follow-up 3 — is that a silent, log-only degradation of a security backstop should have a counter behind it so it can be alerted on.
**Why it matters**: A managed-Redis deployment that silently can't verify its eviction policy has exactly the same operator-blind-spot shape as the original purge-job bug: nothing distinguishes "we checked and it's fine" from "we couldn't check." A misconfigured managed Redis (e.g., `allkeys-lru`) would go undetected indefinitely with no signal besides grepping logs.
**Suggested fix**: Add a small gauge/counter (e.g., `paysplit_redis_eviction_policy_unverified`) alongside the log line, consistent with the alerting pattern used for `SessionPurgeExhaustedTotal`.

## Nits
- ⚪ `internal/bootstrap/app.go:91-94`, the `environment == ""` placeholder string is duplicated logic with `isDevelopment()`'s trim/fold; a small helper (e.g. `cfg.App.DisplayEnvironment()`) would keep the "unset means not-development" framing in one place instead of two.

## Strengths
- The Lua scripts (`internal/platform/session/scripts.go`) for `revokeUser` and `revokeUserSIDs` are cleanly separated with a precise doc comment explaining exactly why the unconditional variant is needed (Postgres/Redis can legitimately disagree about which sessions are "live"), and both are exercised against real miniredis behavior, including orphan-pointer cleanup and "don't kill a session created after the fact" races.
- The auth middleware split (`internal/transport/http/middleware/auth.go`) is exactly the right shape: only `errors.Is(err, session.ErrNotFound)` becomes 401, everything else becomes 503, and `auth_test.go` explicitly tests that a *wrapped* `ErrNotFound` (`fmt.Errorf("get session: %w", err)`) still resolves to 401 while a `context.DeadlineExceeded` or a bare network error resolves to 503 — this is exactly the inversion risk called out in the review brief, and it's covered.
- `TestSessionPurgeWorker_LastAttemptRaisesTheAlarm` / `..._MidRetryDoesNotRaiseTheAlarm` correctly verify the `job.Attempt >= job.MaxAttempts` boundary matches River's own internal discard condition (confirmed against `river@v0.43.0/internal/jobexecutor/job_executor.go:465`), so the alert fires exactly on River's last attempt, not one attempt early or late.
- The `APP_ENV` fail-closed fix is verified through `Load()` end-to-end (`TestLoadTreatsUnsetAppEnvAsNotDevelopment`), not just against a hand-built `Config`, which is the right level to catch the actual bug (the old default lived in `stringEnv`, not in `Validate`).
- `internal/platform/redis/client_integration_test.go` correctly identifies what the miniredis-based unit test can't prove (real go-redis `ConfigGet` response shape) and is explicit that it skips silently without `TEST_REDIS_URL`, consistent with project convention.

## Test coverage
Coverage is thorough across all four follow-ups: session store semantics (create/get/revoke/orphan-pointer cleanup) via miniredis, middleware 401-vs-503 behavior including wrapped-error and leak-nothing cases, purge-exhaustion counter behavior at exact retry boundaries plus a metric-name/type/help contract test, and config validation across unset/explicit/case-insensitive `APP_ENV` combined with password presence. The one gap is behavioral rather than a missing unit test: no test exercises the repeat-lock path end-to-end (usecase + repository together) to show that the purge job is *not* enqueued when Postgres returns zero rows — the existing `TestUpdateAccountStatus_RevokesUnconditionallyEvenWhenNoSessionRowMatched` only proves the synchronous `RevokeUser` call still fires, which is necessary but not sufficient to catch the Major finding above, since it uses a mock repository that doesn't reflect the real `EnqueueTx` no-op behavior.
