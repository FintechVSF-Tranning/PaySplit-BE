## Summary

This is the spec-0011 cutover from JWT + refresh-token rotation to an opaque Redis-backed session ID. The Lua scripts (`create`, `get`, `peek-and-delete`, `revoke-user-sids`) are correct and carefully reasoned: TTL clamping, orphan-pointer cleanup, and SID-matching for the delayed purge job all hold up under inspection and are backed by strong miniredis unit tests. Write-ordering per call site matches the documented table exactly (sign-out Redis-first, sign-in/reset-password/admin-lock Postgres-first, change-password untouched). The two migrations are symmetric (verified against the original `000001` schema for `session_refresh_tokens`). The middleware, config validation (AC-15 invariants), readiness probe, and shutdown ordering are all solid, with excellent targeted unit tests added specifically because the old code path only had integration coverage that silently skips without env vars.

The four known residual risks from the spec's own Risk/Follow-up list (admin re-lock no-op, transient-Redis-outage mass logout, silent purge-job exhaustion, unenforced Redis password/`noeviction`) are present in the code exactly as the spec describes and are out of scope per the review brief — they are not repeated below. The main new gap found is that the spec's own recommendation to add a purge-job backstop at the sign-in and password-reset call sites (not just the mandatory one at admin-lock) was not implemented, which leaves password-reset — the one flow meant to kill a stolen credential — without any convergence path if the direct Redis write fails.

## Major

### 🟠 Password reset has no purge-job backstop if the direct Redis revoke fails, `internal/modules/auth/usecase/service.go:309-318`
**Problem**: `ResetPassword` commits the Postgres password change and revocation first, then calls `s.sessions.RevokeUserSIDs` directly. If that call fails (Redis timeout/network blip), the error is returned to the caller but nothing is enqueued to retry the revocation — unlike the admin-lock path (`internal/modules/admin/repository/postgres/repository.go`, `EnqueueTx` inside the same transaction) there is no `SessionPurgeEnqueuer` wired into the auth usecase or its repository at all (confirmed: no import of `paysplit-backend/internal/modules/auth/jobs` in `usecase/service.go`, and no `SessionPurgeEnqueuer` field/param on `Service`). The stale session then survives until its TTL naturally expires (up to `SESSION_ABSOLUTE_TTL_HOURS`, default 30 days).
The same gap exists for `SignIn`'s "replace old device" case (`internal/modules/auth/usecase/service.go:239-260`), though that one is lower stakes (an old device staying logged in, not a suspected-compromise flow).
**Why it matters**: The spec's own decision table (`docs/specs/0011-redis-session-auth/0003-revocation-backstop.md`, table rows 2 and 4) marks both call sites "mở, cần job" (open, needs a job) and the child spec's build plan explicitly says a job "Nên có ở đặt lại mật khẩu và đăng nhập" (should exist at password reset and sign-in). Password reset is precisely the flow a victim uses to invalidate a credential they believe is compromised; if the one Redis write that kills the old session fails, there is currently zero self-healing path, whereas the admin-lock path (which has the identical failure mode) does converge via `session_redis_purge`. This is a real, undocumented asymmetry: the spec flagged the risk but the implementation only closed it for one of the three call sites where it applies.
**Suggested fix**: Wire the same `SessionPurgeEnqueuer` used by admin into the auth repository/usecase, and enqueue a purge job for `revokedSIDs` inside the same Postgres transaction that revokes them in `ResetPassword` (and optionally `SignIn`'s replaced-session case), mirroring `UpdateAccountStatusWithRevocation`.

### 🟠 `SignIn` — the single highest-risk function in the feature — has no unit test, only a skip-by-default integration test, `internal/modules/auth/usecase/service_test.go`
**Problem**: `service_test.go` has unit tests for `SignUp`, `VerifyEmail`, `ResendVerification`, `ForgotPassword`, `ResetPassword`, `SignOut` (both success and idempotent-miss), and `ChangePassword`, but none for `SignIn`. The only exercise of `SignIn` is `TestAuthHTTPJourney` in `internal/modules/auth/delivery/http/handler_integration_test.go`, which is skipped silently unless both `TEST_DATABASE_URL` and `TEST_REDIS_URL` are set (a trap the task brief itself calls out). `SignIn` contains the Postgres-then-Redis ordering, the compensating `RevokeSession` calls on two different failure branches (`session.NewCredential()` failing, and `s.sessions.Create` failing), and the rate-limit/lockout interplay — all branching, error-handling, and security-relevant logic per the test-adequacy bar for a `TESTS=configured` project.
Separately, `mockSessionStore.RevokeUserSIDs` in the same test file (`service_test.go:74-78`) always returns `(len(sids) > 0, nil)` — it can never return an error — so the "direct Redis revoke fails after Postgres commit" branch in `ResetPassword` (see the Major above) is never exercised even by mock, in either the auth or admin usecase tests.
**Why it matters**: `SignIn`'s compensating-revoke branches are exactly the kind of logic most likely to silently regress (e.g., swapping the order of the two `RevokeSession` calls, or forgetting one) without a fast unit test catching it — the integration test that would catch it does not run in a default `go test ./...` invocation, and `/check verify` runs are not part of every commit.
**Suggested fix**: Add table-driven unit tests for `SignIn` using the existing `mockRepository`/`mockSessionStore` fixtures (which already support injecting errors), covering at minimum: happy path, wrong password with/without lockout, `CreateSession` domain errors, `session.NewCredential()` failure triggering `RevokeSession`, and `sessions.Create` failure triggering `RevokeSession`. Add an error-returning case to `mockSessionStore.RevokeUserSIDs` and a corresponding assertion in `TestResetPassword_ValidatesInputAndUpdatesPassword` (or a new test) that the error propagates.

## Minor

### 🟡 `000018_device_tokens_v1.sql` down migration loses FCM tokens for already-revoked sessions, `db/migrations/000018_device_tokens_v1.sql:47-58`
**Problem**: The down migration restores `sessions.fcm_token` only `WHERE s.revoked_at IS NULL`. Any device token that was backfilled from a since-revoked session (or added via `device_tokens` after the up-migration ran) is dropped permanently when rolling back, since `device_tokens` is then `DROP TABLE`d.
**Why it matters**: Narrow blast radius (only matters if this specific migration is rolled back after having been live long enough to accumulate revoked-session token history), but it is a genuine, silent data loss on rollback that isn't called out anywhere in the migration's own comments (unlike `000019`'s down block, which explicitly documents that refresh-token data is unrecoverable).
**Suggested fix**: Either restore tokens for all sessions regardless of `revoked_at` (last-write-wins per device is already the stated semantics), or add a comment acknowledging the same "data loss on rollback" caveat that `000019` states explicitly.

## Nits

## Strengths

- The four Lua scripts in `internal/platform/session/scripts.go` are genuinely well-designed: TTL clamping is enforced inside Lua (not just at the Go layer), the orphan-pointer problem is solved symmetrically in both `createScript` (killing the old session hash) and `revokeUserSIDsScript` (cleaning up a pointer left behind by `getScript`'s absolute-expiry deletion), and the SID-matching in `revokeUserSIDsScript` is exactly what makes the delayed purge job safe to retry — all of this is backed by direct miniredis tests (`store_test.go`) that assert the specific race conditions the comments describe, not just the happy path.
- `internal/transport/http/middleware/auth_test.go` and `internal/platform/redis/client_test.go` are new, focused, dependency-free unit tests added specifically to close a real coverage gap (the old code was only exercised through integration tests that silently skip); `TestAuth_ErrorResponseLeaksNothing` is a nice touch, directly testing the security property that a Redis-outage response must be indistinguishable from a not-found response.
- Migration `000019`'s down block is exemplary: it recreates `session_refresh_tokens` byte-for-byte identical to the original `000001_init_schema.up.sql` definition (confirmed by diff) and explicitly documents the one piece of data that cannot be restored (raw refresh tokens), rather than pretending the rollback is lossless.
- Write-ordering at every call site matches the documented table in `0003-revocation-backstop.md` exactly, with the reasoning inlined as a comment at each site — this makes the trade-off auditable without cross-referencing the spec.

## Test coverage

Strong coverage of the new infrastructure: `internal/platform/session/store_test.go` and `store_integration_test.go` cover all four Lua scripts including the TTL-clamping, orphan-pointer, and delayed-retry-safety scenarios; `internal/platform/redis/client_test.go` covers fail-fast connection behavior and readiness-probe semantics; `internal/transport/http/middleware/auth_test.go` covers the context-injection invariant and the "identical error response regardless of failure reason" security property; `internal/modules/auth/jobs/session_purge_test.go` covers the purge worker's idempotency and error-propagation. `internal/config/config_test.go` covers both new AC-15 invariants (idle-vs-absolute TTL, retention-vs-drift).

The gap is at the usecase layer: `SignIn` (the most consequential function touched by this spec) has no unit test at all, relying entirely on an integration test that is skipped by default (see Major above), and no test in the suite exercises a `RevokeUserSIDs` failure returning a non-nil error (the mock cannot produce one), so the compensating-error paths in both `ResetPassword` and admin's `UpdateAccountStatus` are unverified by anything faster than the full integration/verify suite.
