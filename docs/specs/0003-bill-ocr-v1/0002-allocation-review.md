# 0002. Allocation and review

## Summary

This child spec covers full draft replacement, exact ratio assignments, provisional share calculation, reconciliation, optimistic locking, and explicit review. One calculation function serves both preview and finalize so users see the amounts that will become financial records.

## Requirements

This child owns **AC-5** through **AC-8**, preview reads in **AC-12**, and split performance in **AC-14** from [the umbrella spec](index.md).

## Decision

The mobile client sends one complete draft document with the version it read. The usecase validates and replaces bill fields, items, and assignments in one short transaction. Assignments store exact decimal ratios in `(0, 1]`, while every monetary result uses integer VND and Hamilton allocation.

## Feature design

### Full draft replacement

1. Only the Creditor for their bill or the Captain may replace a draft.
2. The request carries `version`, bill fields, up to 100 items, and each item assignment set.
3. The service validates JSON shape, sizes, numeric ranges, and duplicate request IDs before opening a transaction. It then locks the bill and validates version, state, group scope, active assignees, ratio sums, and child ownership before replacing rows.
4. Stable client item IDs are UUID v7 values generated by the mobile app. The service rejects duplicates, cross bill references, cross group members, and inactive assignees during save.
5. The response returns the committed bill, new version, reported totals, `computed_subtotal`, `computed_total`, stable mismatch codes, and provisional member breakdown.

### Reconciliation

1. `line_total` is independent from quantity times unit price.
2. `computed_subtotal` equals the sum of line totals. Reported `subtotal` is stored separately.
3. `computed_total` equals reported subtotal plus service charge plus VAT minus discount. Reported `total` is stored separately.
4. Discount cannot exceed subtotal plus service charge plus VAT.
5. A mismatch may be stored on a draft and is visible through `SUBTOTAL_MISMATCH` or `TOTAL_MISMATCH`, but review and finalize are blocked until reported and computed values match.

### Ratio and preview calculation

1. Every item must have one or more assignment rows before review.
2. Each `share_ratio` is `numeric(9,8)` in `(0, 1]`. The per item sum is exactly `1.00000000`.
3. Equal split sorts member UUIDs by canonical 16 byte order and writes ratios for the selected members. When equal decimal ratios cannot sum exactly at eight digits, the last UUID receives the residual so the sum is exact. Money fairness still comes from Hamilton.
4. Each line total is apportioned by ratio. Hamilton assigns remaining VND by largest fractional remainder, then canonical ascending member UUID byte order. Go and PostgreSQL tests must prove the same ordering.
5. Service charge, VAT, and discount are each apportioned in proportion to member item subtotal using the same tie rule.
6. If subtotal is zero, service charge, VAT, and discount belong to the Creditor. Discount must still satisfy the bill formula.
7. Each item, service charge, VAT, and discount runs its own Hamilton allocation. Final amount is item subtotal plus service share plus VAT share minus discount share. `rounding_adjustment` is the sum of each component result minus truncation toward zero of that component exact rational share, with discount contribution subtracted. The mobile client can identify who absorbed indivisible VND.

### Review

1. Review requires the Creditor or Captain, a reconciled draft, valid assignments, active assignees, and the exact current version.
2. Review stores actor and time on the bill without changing semantic data. It writes an activity and returns the reviewed version.
3. Editing fields, items, assignments, or applying OCR increments version and clears review. Images cannot change after creation.
4. An OCR job completing without application does not change the bill and does not clear review. A reviewed bill may still show a newer unapplied candidate.

### Concurrency and limits

1. Every semantic mutation locks the bill first. Child rows are then locked in canonical UUID byte order where needed.
2. A stale version returns `409 VERSION_CONFLICT` with the current version and no partial writes.
3. Preview calculation runs in memory from one bounded document. No per item or per member query loop is allowed.
4. At 100 items and 50 members, unit and benchmark coverage must demonstrate the 50 ms calculation target on the supported test environment.

## Build plan

1. Add ratio, review, version, constraint, and query changes with PostgreSQL tests, satisfies **AC-5** through **AC-7**.
2. Implement one pure allocation package for item, charge, discount, zero subtotal, overflow, and deterministic Hamilton behavior, satisfies **AC-6** and **AC-14**.
3. Build full draft replace through repository, usecase, HTTP, idempotency, activity, and OpenAPI, satisfies **AC-5**, **AC-6**, and **AC-8**.
4. Build review and invalidation behavior with concurrent writer coverage, satisfies **AC-7**.
5. Complete preview response, bill detail integration, bounds tests, and performance metrics, satisfies **AC-6**, **AC-12**, and **AC-14**.

## Rationale

One complete document avoids partial states where items and assignments describe different versions. Exact stored ratios match the mobile percentage model. Integer Hamilton calculation prevents money loss, and versioned review makes the human approval requirement observable rather than inferred from an earlier save.
